An LLM whose layers do not live on any single machine. They are split across devices that find each other on their own — nothing coordinates them. If one leaves, the model cannot think, and the screen says so before you ask.

§ 01 The problem

Running a model means owning one machine big enough to hold all of it. Models grow faster than the machines do, so the accepted answer is to rent someone else's server: your prompts leave your network, and the day that server is down — or decides you are not welcome — you have nothing.

Meanwhile the room is full of idle GPUs. Every laptop at the table could hold a piece of the model. Nothing lets them hold it together.

§ 02 The solution

Split the model itself. Llama 3.2 3B has 28 layers; Shard hands each machine a range of them. No machine holds the whole model, and no server decides who holds what — every node runs the same arithmetic over the same peer list and reaches the same answer on its own.

§ 03 The stack

01 · Distribution

Pear + Bare

The app ships as a standalone binary over Hyperdrive. Updates travel as deltas to running instances — an 80MB binary costs about 6MB on the wire.

02 · Discovery

UDP on the LAN

Nodes announce themselves by sweeping the local subnet. Hyperswarm could not hole punch between two firewalled laptops, so on the LAN we do not ask it to.

03 · Planning

No coordinator

Peers are sorted by a stable id and layers are handed out in order. Every node computes the same plan independently. Nothing votes, nothing is elected.

04 · Inference

llama.cpp RPC

Each machine runs a ggml-rpc-server holding its layers in GPU memory. The asking node drives them all through one --rpc list.

§ 04 Deployment procedure

Five steps, on every machine that will serve layers. Steps 01 to 03 are one-time setup; after that, Shard updates itself over the air.

Step 01

Install the Pear runtime

Shard is not on npm and has no download page. It is fetched peer-to-peer by the Pear runtime, so that comes first. Needs Node 22 or newer.

npm i -g pear
pear

Running pear once with no arguments finishes the setup.

Step 02

Build llama.cpp with RPC

This is what actually holds the layers and does the math. The RPC backend is off by default, so it has to be compiled in. On Apple Silicon add Metal for the GPU.

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_RPC=ON -DGGML_METAL=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j8

This produces build/bin/ggml-rpc-server and build/bin/llama-cli, which is what Shard looks for.

Step 03

Get the model

Shard does not distribute the weights — each machine fetches the same GGUF itself. About 1.9 GB.

mkdir -p ~/models
curl -L -o ~/models/Llama-3.2-3B-Instruct-Q4_K_M.gguf \
  https://huggingface.co/bartowski/Llama-3.2-3B-Instruct-GGUF/resolve/main/Llama-3.2-3B-Instruct-Q4_K_M.gguf

Shard searches the working directory first, then $HOME.

Step 04

Install Shard, peer-to-peer

No registry, no CDN, no release page. The app arrives from whoever is seeding it, addressed by key. The target directory has to exist first.

mkdir -p ~/shard
pear install --to ~/shard pear://k6c99su98pmobmw1c4xqtoacsage1is5ayhq9mqdsc8gobdzg8bo

On macOS the first run asks for Local Network permission. Without it, discovery finds nobody.

Step 05

Run one command per machine

--offer is how many GB of layers this machine lends; at roughly 68 MB per layer, 1 GB is about 15 layers. Give each machine its own port.

# machine one
~/shard/hello-pear-bare --label laptop1 --port 50053 --offer 1

# machine two
~/shard/hello-pear-bare --label laptop2 --port 50052 --offer 1

Then open localhost:7777 on either machine. The panel shows the split live, and the band turns amber the moment the 28 layers are covered.

One line to start

Pull the app off the network

The whole install is a key. Nothing in the middle decides whether you are allowed to have it.

pear install --to ~/shard pear://k6c99su98pmobmw1c4xqtoacsage1is5ayhq9mqdsc8gobdzg8bo

§ 05 Known limitations

Read before deploying on a network you do not control
  • It does not cross subnets. Discovery is LAN-only. Two machines on different networks will not find each other.
  • It does not punch through symmetric NAT. Two peers both behind it need a relay, which the Pear CLI does not expose.
  • The RPC link is neither encrypted nor authenticated. Anything on your LAN that reaches the port can use your GPU.
  • It cannot prove a peer really ran your layers. No attestation, no verification. You are trusting the machines you invited.
  • There is no redundancy. Every layer has exactly one owner. One machine leaving breaks the model until it returns.
  • It does not distribute the model. Each machine downloads the GGUF itself.
